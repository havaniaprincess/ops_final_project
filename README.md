# Итоговый проект по курсу "Инфраструктура и администрирование"

Итоговый проект, призванный показать компетенции Operation systems, на примере простого http-сервера.

## Краткое описание

HTTP-сервер написанный на `RUST`, с использованием библиотеки `axum` для роутинга endpoint-ов. Для логирования использовалась библиотека `log` и `env_logger`. Сервис предоставляет простой сайт и несколько базовых get-ендпоинтов.

## Сам сервис

Что сервис умеет для пользователя:

- **Back-end** для сайта. На данный момент там простенький сайт позволяющий следить за наложением событий в проекте друг на друга, когда они начинаются и заканчиваются.(endpoint-ы для `html`, `js`, `css`)
- **Other Endpoints**
    - `/health` - возвращает статус 200 - Success
    - `/temp_converter?celsius=<f64>` - возвращает переведенные в Фаренгейты цельсии
    - `/version` - возвращает форматированную строку содержащую версию сервиса, версию компилятора и автора.
    - `/docs` - возвращает документацию к сервису

Что сервис еще умеет внутри:

- `unit-test-ы` - сервис полностью покрыт на 90-95%
- `logging` - сервис логирует каждый запрос, по какому endpoint-у он пришел, какой ответ получил(статус) и за сколько был выполнен. Запись логов в файл выполняется в отдельном потоке

## Схема архитектуры

Путь запроса: клиент → nginx (TLS, редирект 80→443) → app:APP_PORT. Плюс certbot продлевает сертификат каждые 12 часов, nginx перечитывает конфиг каждые 6 часов, логи лежат в volume app_logs, Docker работает в rootless-режиме.

## Окружение

Для запуска сервиса требуется система сборки `cargo` которую можно установить по инструкции разработчиков: [Rust Book. Installation.](https://doc.rust-lang.org/book/ch01-01-installation.html)

В проекте находится файл `Cargo.toml` где и указаны все настройки проекта, включая зависимости, настройки сборки, тестов и прочее. При компиляции компилятор все скомпилирует в папку `target` бинарник будет лежать по пути `./target/debug/ops_app` или `./target/release/ops_app`. Поэтому это и есть окружение проекта.

## Переменные окружения

Список переменных окружения требуемых сервису:

- `LOG_FILE` путь к файлу с логами(по умолчанию `logs/server.log`)
- `APP_PORT` порт сервиса(по умолчанию `3000`)
- `RUST_LOG` уровень логирования(по умолчанию `info`)

Остальные переменные требуемые при деплое:

- `APP_NAME` имя приложения(бинарного файла)
- `DOMAIN` и `EMAIL`
-  `HTTP_PORT` и `HTTPS_PORT`

## Переменные сборки 

- `CARGO_PKG_VERSION` версия сервиса, сборщик создаст сам
- `CARGO_PKG_AUTHORS` автор сервиса, сборщик создает сам
- `CARGO_CRATE_NAME` имя бинарника, сборщик создает сам
- `RUSTC_VERSION` версия компилятора, создается при сборке кодом в файле `build.rs`

## CI on GitHub

GitHub при каждом pull request и push выполняет тестирование версии, которое состоит из:

- `fmt`: тест форматирования кода
- `clippy`: статический анализ кода, поиск неэффективностей, потенциальных ошибок
- `test`: тестирование юнит тестами.
- `docs`: компиляция документации
- `coverage`: тест покрытия кода тестами
- `audit`: тест на уязвимости, нарушение лицензий
- `build`: Билд бинарных файлов.

Некоторые выгружают артефакты(сборки, покрытие тестами, результаты тестов, анализ кода)

## CD on GitHub

GitHub запускает деплой на сервере посредством ssh и сам после отработки деплоя проверяет работоспособность сервиса(endpoint-ы `/health` и `/version`). На виртуальной машине настроен доступ по данному ключу только для деплоя коммитов. Если используемый ключ пытается выполнить что-то другое, у него не получится, скрипт, который обрабатывает все коннекты по ключу не даст запустить скрипт деплоя(`./deploy.sh`).

### `./deploy.sh`

```text
./deploy.sh [команда] [опции]
./deploy.sh --help
```

#### Команды

| Команда | Что делает |
|---|---|
| `up` *(по умолчанию)* | Собирает образ приложения, при необходимости получает сертификат, поднимает все контейнеры и ждёт, пока сервис ответит на `/health` |
| `status` | Показывает состояние контейнеров и проверяет `/health` |
| `restart` | Перезапускает контейнеры **без пересборки** и проверяет `/health`. Новый код так не попадёт — для этого `up` |
| `down` | Останавливает и удаляет контейнеры. Сертификаты (`certbot/`) и volume с логами сохраняются |
| `logs [сервис]` | Логи контейнеров в реальном времени (последние 100 строк + новые). Можно указать сервис: `./deploy.sh logs nginx` |
| `app-logs` | Лог запросов приложения (`/app/logs/server.log` в volume `app_logs`) в реальном времени |

#### Что происходит при `up`

1. **Проверки окружения.** Есть ли Docker и docker compose, доступен ли демон.
2. **Проверка `.env`.** Если файла нет — создаётся из `.env.example`, и скрипт останавливается с просьбой его заполнить.
   Скрипт также не даст запуститься, если:
   - не заданы `APP_NAME`, `DOMAIN` или `EMAIL`;
   - остались значения-примеры `example.com` / `admin@example.com`;
   - `APP_NAME` не совпадает с именем бинарника в `Cargo.toml` (`ops_app`) — иначе сборка образа упадёт.
3. **Сборка образа** приложения.
4. **Сертификат.** Если настоящего сертификата для `DOMAIN` ещё нет (или указан `--force-cert`):
   - создаётся временный самоподписанный сертификат — без него nginx не стартует;
   - запускается nginx — он нужен Let's Encrypt для проверки домена;
   - certbot получает настоящий сертификат;
   - nginx перечитывает конфиг с новым сертификатом..
5. **Запуск всех сервисов.**
6. **Проверка `/health`** — до 30 секунд, запрос идёт через nginx, тем же путём, что и реальный трафик.

## Варианты запусков

Чтобы `/docs` работал при локальном запуске, нужно скопировать `target/doc` в `doc/` (в Docker это делает Dockerfile).

### Только сервис

```
cargo run --release
```

Требуется установленный сборщик `cargo`. Сервис будет доступен по пути `localhost:3000`

### Ансамбль Docker'ов

#### 1. Настройки

```bash
cp .env.example .env
```

В `.env` поменять:

```ini
APP_NAME=ops_app      # должно совпадать с именем бинарника в Cargo.toml
DOMAIN=localhost
EMAIL=dev@localhost   # локально не используется, но должно быть задано
```

Порты 80/443 можно оставить, если они свободны. Сменить их нужно, если:
- порты заняты другим веб-сервером;
- используется **rootless Docker** на Linux — обычный пользователь не может открыть порты ниже 1024
  (на сервере это решается через sysctl, см. [DEPLOY.md](DEPLOY.md)).

```ini
HTTP_PORT=8080
HTTPS_PORT=8443
```

#### 2. Самоподписанный сертификат

nginx ищет сертификат в `certbot/conf/live/$DOMAIN/`, без него он не стартует.

**Вариант A — через Docker** (работает на любой ОС, openssl ставить не нужно):

```bash
docker compose run --rm --no-deps --entrypoint sh certbot -c "mkdir -p /etc/letsencrypt/live/localhost && openssl req -x509 -nodes -newkey rsa:2048 -days 365 -keyout /etc/letsencrypt/live/localhost/privkey.pem -out /etc/letsencrypt/live/localhost/fullchain.pem -subj /CN=localhost -addext subjectAltName=DNS:localhost,IP:127.0.0.1"
```

**Вариант B — openssl на хосте** (Linux, macOS, Git Bash):

```bash
mkdir -p certbot/conf/live/localhost
```

```bash
openssl req -x509 -nodes -newkey rsa:2048 -days 365 \
  -keyout certbot/conf/live/localhost/privkey.pem \
  -out certbot/conf/live/localhost/fullchain.pem \
  -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
```

В Git Bash на Windows путь `/CN=localhost` превращается в путь Windows и openssl падает —
перед командой нужно добавить `MSYS_NO_PATHCONV=1 `.

`subjectAltName` обязателен: без него Chrome и Firefox отвергают сертификат даже после подтверждения исключения.

#### 3. Запуск

```bash
docker compose up -d --build nginx app
```

```bash
docker compose ps
```

#### 4. Проверка

Сайт: <https://localhost> (или <https://localhost:8443>, если меняли порты).
Браузер предупредит о небезопасном сертификате — это ожидаемо для самоподписанного, нужно подтвердить исключение.

```bash
curl -k https://localhost:8443/health -o /dev/null -w "%{http_code}\n"
```

`-k` отключает проверку сертификата у curl, ожидаемый ответ — `200`.

> Если порты изменены, открывайте сразу `https://…:8443`. Запрос на `http://localhost:8080`
> nginx перенаправит на `https://localhost/` — **без порта**, то есть на 443, где ничего не слушает.

#### 5. Остановка

```bash
docker compose down
```

Сертификат в `certbot/conf/` остаётся, при следующем запуске его не нужно создавать заново.

## Безопасность

- защита от выхода из папки во всех файловых хендлерах;
- rootless Docker;
- ключ CD ограничен forced command;
- вход по SSH только по ключу;
- HSTS.
